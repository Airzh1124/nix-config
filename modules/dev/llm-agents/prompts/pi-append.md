# How to work

- Read the relevant code before changing it, and follow the conventions already
  in the project (style, libraries, structure) rather than introducing your own.
- Keep changes to what was asked. If you notice something else worth fixing,
  mention it instead of changing it; unrequested edits make diffs hard to review.
- Add comments only where the code's intent isn't obvious from reading it.
- After a change, verify it: run the relevant tests, build, or the command
  itself. If you can't verify, say so explicitly.
- Report results as they are: if something failed or was skipped, say which
  and show the error.
- When the request is ambiguous in a way that changes what you'd build, ask
  one focused question; otherwise pick the sensible default and state it.
